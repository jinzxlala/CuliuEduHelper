# ADR 0004：版本化中文搜索金标评测

- 状态：Accepted
- 日期：2026-08-02

## 背景

知识来源、搜索契约和正式导入链路已经建立，但在加入同义词、字段权重调整、向量或混合检索前，需要一个可重复、可审计的中文检索基线。项目设计要求至少50条顾问标注查询、Top-5命中率不低于85%、关键查询100%、硬过滤100%以及P95低于500ms。

当前正式索引为48条讲座、169张匿名案例卡和0条逐字稿正文。逐字稿仍受隐私硬门禁保护，因此不能为了凑齐评测范围而向正式索引写入虚构片段。

## 决策

1. 使用`knowledge/search-gold.v1.json`保存版本化查询fixture，并绑定`corpus_id + corpus_hash + mapping_version + manifest_version`。任何语料或映射变化都必须显式升级并复核评测集。
2. 每条查询记录目标索引、结构化搜索输入、预期ID、禁止命中ID、关键级别、标签和说明。相同目标与搜索输入不得复制成多条来抬高命中率；fixture至少包含真实启用的硬过滤和禁止命中检查。Top-5通过定义为返回结果中至少包含规定数量的预期ID；禁止命中和硬过滤单独计算，不能被总体召回率抵消。
3. 评测器通过现有`KnowledgeSearchService`执行，不绕过服务端Schema或过滤构造。延迟使用调用方观察到的端到端时间，而不只采用Meilisearch内部处理时间。
4. 技术门禁和业务批准分离。Code Agent起草的fixture保持`draft`；只有项目负责人逐条核对后才可记录审核人、时间并改为`approved`。`--require-approved`同时要求技术与审批门禁通过。
5. 当前fixture只评估有正式数据的`lectures`和`cases`。Schema和评测器已经支持`transcript_segments`；解除逐字稿隐私门禁后必须升级fixture并加入时间戳证据查询，阶段1才可能完成完整业务验收。
6. 评测建立前及首次基线阶段不加入同义词、向量、混合召回或按结果反向修改索引配置。真实失败应保留为失败证据，再决定是否调优。

## 结果

- 搜索变更可以在相同语料和查询集上回归，召回、关键查询、过滤、禁止命中与延迟具有明确口径。
- 技术全绿不再被误报为业务已确认；`draft`评测集的`release_gate_passed`固定为`false`。
- 当前无法验收逐字稿时间戳搜索，这一缺口被显式保留，而不是由虚构数据掩盖。
- 项目负责人需要承担一次逐条业务标注工作；后续查询修改需在Git差异和fixture版本中可见。
