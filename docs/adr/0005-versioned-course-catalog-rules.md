# ADR 0005：版本化课程目录与确定性规则引擎

- 状态：Accepted
- 日期：2026-08-02

## 背景

MVP 的课程规划不能直接依赖模型凭经验判断先修、互斥、年龄、时间冲突和学习负荷。这些条件需要可复核、可测试，并且在课程或规则变化后能准确识别规划所依据的历史版本。当前仓库尚无获批的真实课程目录，因此本模块只能建立数据结构、审批流程和使用虚构数据的测试，不能宣称课程业务数据已经准备完成。

## 决策

1. `course` 与 `course_rule` 保存稳定身份；`course_version` 与 `course_rule_version` 保存不可变内容。修订必须创建带来源指针的新版本，禁止原地改写或从同一来源分叉。
2. 版本状态为 `draft → approved → archived`，也允许草稿直接归档。只有当前有效的 `admin` 可以创建、修订、批准或归档；`advisor`、`auditor` 可以读取已批准快照并执行确定性评估。MVP 暂不增加独立课程研发角色，待账号管理界面和职责决定后再拆分权限。
3. PostgreSQL 是正式目录来源。服务层实施乐观并发、审计和易读错误；数据库约束与触发器再次保护管理员身份、版本链、不可变内容、课程时段、审批状态、规则引用和课程可用性，防止绕过服务层写入无效数据。
4. 规则引擎只负责五类显式规则：先修课程、课程互斥、年龄范围、时间冲突和负荷上限。硬规则决定是否可选，`warning` 只生成提示；模型不得覆盖规则结果。
5. 规则批准前必须整体编译已批准快照，拒绝重复规则、先修与互斥矛盾、无交集年龄范围和先修循环。相邻但不重叠的时段允许选择；先修课程必须在历史完成集合中，不能用同期开课替代。
6. 课程规划、替代方案、规则例外记录、推荐理由和 Markdown 导出属于后续模块。本模块不调用 DeepSeek，也不引入 Skill Runtime；`student-course-plan` 仅作为需求与测试设计参考，不在运行时加载。

## 结果

- 后续规划可以固定引用已批准的课程版本和规则版本，避免目录变化静默改变旧规划含义。
- 课程业务人员仍需提供并批准真实课程目录；当前所有测试课程均为明确标注的虚构数据，且只存在于随机临时测试数据库。
- 规则变更需要新版本和人工批准，增加了操作步骤，但换来可审计性、可回归性和稳定的规划输入。
- 当前 `admin` 同时承担目录维护与批准，是一人协作 MVP 的有意简化；上线多人协作前应评估职责分离。
