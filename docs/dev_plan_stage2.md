# CuliuEduHelper 第二阶段开发计划：学生画像与课程规划联动

> 文档状态：已确认开发计划
>
> 更新日期：2026-08-03
> 开发方式：1 名项目负责人，与 Codex、Claude Code 等 Code Agent 协作

## 1. 目标与交付标准

在现有“学生事实—证据—画像审核—人工课程规划”基础上形成闭环：

`批量建档 → 文件增量提取 → 顾问逐条确认 → 画像复查/重建 → 课程推荐 → 班级课表优化`

本阶段交付：

- 支持通过 `.txt`、`.md`、`.docx`、`.csv` 文件批量导入学生基础信息；
- 支持从 CSV 教学反馈和 DOCX 会议逐字稿中提取指定学生的增量事实；
- 每条模型建议均可修改、接受或拒绝，模型不得直接更新正式画像；
- 保留现有手动事实、证据和画像编辑功能；
- 将稳定课程模板与实际开班信息分层维护；
- 根据已批准画像推荐课程模板，并匹配当前可选的实际班级；
- 使用整数规划为地点已经确定的班级分配合适教师并选择上课时段；
- 保留完整的版本、审核、审计、隐私控制和失败恢复能力。

参考教学反馈文件：

`D:\workshop\学生项目规划\学生后续课程规划\USACO-basis\教学反馈_贝赛思【USACO Silver】-周三.csv`

该文件采用“日期、公共课程内容、每名学生独立反馈列”的结构，个别学生单元格还包含独立的课程日期、教师和课程内容。因此解析必须以学生列和单元格内部结构为准，不能简单按整行共享课程信息。

## 3. 学生基础信息批量导入

### 3.1 基础字段

家长提供的基础信息映射为以下稳定字段：

| 业务内容 | 字段键 | 结构 |
|---|---|---|
| 学员姓名 | `identity.name` | `chineseName`、`englishName`，无英文名时保存 `null` |
| 学员年级 | `academic.grade` | 原始年级及标准化年级 |
| 出生日期 | `identity.birth_date` | ISO 日期及原始文本 |
| 就读学校 | `academic.school` | 学校名称及可选标准化名称 |
| 家长电话 | `contact.parent_phone` | 规范化号码及原始地区信息 |

这些字段继续以版本化学生事实保存，不直接加入模型画像出站白名单。姓名、出生日期和电话均按敏感信息处理。

### 3.2 导入流程

1. 管理员上传 `.txt`、`.md`、`.docx` 或 `.csv` 文件，单文件不超过 20 MB；
2. 原始文件进入管理员专用、不可变的受限导入对象域，不能直接复制到某一学生的证据目录；
3. 服务端先本地识别电话、日期、CSV 行列和文档段落，并将文件拆成候选学生记录；
4. 家长电话在模型出站前由服务端确定性提取并替换为占位符；DeepSeek 只接收完成姓名、年级、学校和记录结构识别所需的最少文本；
5. DeepSeek 返回严格 JSON，服务端执行 Zod Schema、日期、字段集合、长度和来源定位校验；
6. 页面展示候选学生、识别字段、原文定位、重复候选和校验警告；
7. 管理员为每个候选选择“创建新学生”“关联已有学生”或“跳过”；
8. 只有管理员显式确认后，系统才创建学生、学生级证据摘录和版本化事实。

姓名或家长电话相同只能作为重复提示，不能自动合并。兄弟姐妹可能共用家长电话；存在多个匹配候选时必须人工决定。

### 3.3 隐私与证据边界

- 每次模型出站前必须显示确认项，记录出站策略版本、模型、提示词、Schema 和输入哈希；
- Worker 任务只携带批次 ID、授权上下文引用和版本身份，不携带完整学生文本或电话；
- 多学生原始文件只能由管理员读取；普通顾问不得通过学生页面看到其他学生内容；
- 确认导入时，为每名学生生成仅包含该学生来源片段的不可变证据对象，并保存其与原始批次、CSV 单元格或文档段落的派生关系；
- 日志、错误、队列和审计只保存安全元数据，不保存家长电话、原始文件正文或 DeepSeek 原始响应。

## 4. 文件驱动的增量画像更新

### 4.1 支持来源

- 教学反馈 CSV；
- 学生与家长沟通会议的现代 Word `.docx`；
- 后续可扩展为 Markdown、文本、成绩单和项目记录，但不在本阶段默认开放未定义格式。

### 4.2 指定学生提取

增量提取只能从某一已授权学生的详情页发起：

- CSV 通过已确认的中文名、英文名和别名定位目标学生列，只截取该学生的课程内容与反馈；
- 如果学生单元格内包含独立课程名称、时间或教师，以单元格内信息优先，不强行继承公共课程列；
- DOCX 提取正文后，先检查是否包含目标学生身份或由顾问确认文件归属；
- 发送 DeepSeek 前替换学生姓名、家长电话、公开编码、邮箱和长身份证明；
- 模型只能从目标学生片段提取事实建议，不能引用同文件中其他学生的信息；
- 本地代码创建证据定位映射，模型只能返回本地 `sourceRef`，不能生成数据库证据 ID。

### 4.3 建议审核与正式写入

每条提取建议保存：字段键、建议值、信息性质、置信度、来源定位、模型版本、提示词版本、Schema 版本和状态。

状态流转为：

`pending → accepted/rejected`

使用者可以：

- 修改建议字段和值；
- 逐条接受；
- 逐条拒绝；
- 对整组建议执行批量接受或拒绝，但最终仍保存每条决定；
- 查看建议对应的原始证据片段。

接受建议时，系统在单一数据库事务中：

1. 重新验证授权、学生、来源对象和定位；
2. 创建新事实或修订当前事实；
3. 将事实绑定至同一学生的合法证据定位；
4. 将建议标记为已应用并记录生成的事实 ID；
5. 将依赖旧事实快照的画像和规划标记为 `needs_review`。

拒绝建议不得修改学生事实。重复接受、并发修订和过期页面提交必须通过幂等键与 `expectedUpdatedAt` 阻断。

### 4.4 与学生画像联动

新事实写入后不自动改写画像，也不自动生成模型草稿：

1. 现有已批准画像被标记为需要复查；
2. 页面显示新增、修订和存在矛盾的事实；
3. 顾问确认输入范围后，手动触发现有画像草稿任务；
4. 新画像草稿使用新的冻结输入快照；
5. 顾问继续使用现有修改、提交、退回和批准流程。

现有手动证据上传、事实录入、事实修订、画像编辑和画像批准功能必须完整保留。

## 5. 课程模板与实际班级

### 5.1 两层数据模型

现有 `course` 和 `course_version` 继续表示稳定课程模板，保存：

- 课程名称和代码；
- 阶段、难度、摘要和目标；
- 能力、学科和项目标签；
- 先修、互斥、年龄、负荷等规则；
- 总课时、预期成果和不适用条件。

新增实际班级实体，保存：

- 课程模板版本；
- 班级名称；
- 可授课教师范围或所需教师资质；
- 固定上课地点；
- 开课和结课日期；
- 周课或短期营类型；
- 单次课时；
- 班级业务优先级；
- 班级状态；
- 文本学生名单。

学生名单本阶段只以文本数组保存，不建立学生画像外键，不用于画像事实、推荐规则或排课约束。

### 5.2 教师、地点与候选时段

教师信息包括：姓名、启用状态、可教授的课程模板或能力标签、每周可用时间、不可用日期、最大每日课时和最大每周课时。

地点信息包括：名称、启用状态、可用时间和临时不可用日期。地点在排课运行前已经分配给班级；教师在运行前尚未分配，求解器需要从满足课程资质和班级限制的教师集合中选择授课教师。

每个班级维护一个或多个完整候选课表：

- 周课候选：指定星期、开始时间和结束时间，系统根据起止日期展开每周一次的全部课次；
- 短期营候选：保存连续日期范围或显式日期集合，展开每天的全部课次；
- 每个候选方案保存偏好惩罚值，用于表达非首选时段；
- 已批准或锁定的班级课表作为后续求解的固定占用资源。

课程模板修订不得修改历史班级；班级修改形成独立版本或审计记录。

## 6. 基于学生画像的课程推荐

### 6.1 冻结输入

推荐任务输入必须冻结：

- 已批准的学生画像版本及 claim ID；
- 当前已确认事实；
- 已完成和正在学习的课程；
- 学生兴趣、可用时间和明确限制；
- 当前批准的课程模板、课程规则和实际班级快照；
- 模型、提示词、Schema、脱敏和计价版本。

画像处于 `needs_review`、没有已批准画像或输入事实已经失效时，不允许生成新的正式推荐草稿。

### 6.2 规则优先、模型解释

确定性规则引擎先排除：

- 硬性先修不满足；
- 年龄或阶段不适合；
- 与已完成课程重复；
- 课程互斥；
- 明确时间冲突；
- 当前负荷超限。

DeepSeek 只能在规则引擎返回的合格候选集合中生成推荐，不得创造课程、班级或画像结论。

推荐草稿包含：

- 1—3 个课程模板推荐；
- 当前可选实际班级；
- 与画像优势、兴趣、待提升点的对应理由；
- 知识衔接、预期成果和风险；
- 支持该推荐的合法画像 claim ID；
- 没有合适班级时仍保留课程方向，并明确“当前无可选班级”；
- 至少一项替代课程或替代路径。

服务端必须验证模型返回的课程版本、班级和 claim ID 均来自冻结快照。模型输出只进入草稿，不能自动加入班级名单或批准规划。

### 6.3 与现有规划联动

- 顾问可以编辑、接受或拒绝课程推荐；
- 接受的推荐可预填入现有人工课程规划工作台；
- 现有两条中立路线、短期课程、重叠/缺口、风险和决策时间线继续由课程规划领域模型保存；
- 课程、规则、画像或班级变化时，受影响推荐和规划标记为 `needs_review`；
- 模型不可用时，顾问仍可以使用现有人工规划功能。

## 7. 基于整数规划的教师分配与班级课表优化

### 7.1 求解范围

本阶段同时选择授课教师和上课时段：

- 教师在运行前尚未分配给班级；
- 地点在运行前已经分配给班级；
- 不执行学生自动分班；
- 文本学生名单不参与冲突检测；
- 求解器从每个班级允许的教师与完整候选课表组合中选择一个方案。

### 7.2 决策变量与硬约束

为每个“班级—候选教师—候选课表”创建二进制决策变量。只有教师具备对应课程资质并满足班级的教师限制时，才能创建该组合变量。

硬约束包括：

- 同一班级最多选择一个候选方案；
- 已标记为必须开设的班级应优先安排，但允许在整体不可行时返回未排原因；
- 分配给班级的教师必须具备该课程模板要求的授课资质；
- 同一教师的所有展开课次不得重叠；
- 同一地点的所有展开课次不得重叠；
- 所有课次必须落在教师和地点可用时间内；
- 所有课次必须位于班级起止日期内；
- 教师每日和每周总课时不得超过限制；
- 已锁定课表不能被求解器移动；
- 周课和短期营候选中的任一课次冲突时，该完整候选方案不可选。

### 7.3 优化目标

按以下优先级进行词典序优化：

1. 最大化已排班级的业务优先级总和；
2. 减少非首选时段惩罚；
3. 减少教师非首选班级或非首选时段的惩罚；
4. 减少同一教师当天课程之间的无效空档；
5. 使用稳定 ID 进行确定性平局处理，使相同输入获得相同结果。

使用 Worker 运行固定版本的 HiGHS WASM 整数规划求解器。依赖固定为 `highs@1.15.2`，部署包必须包含对应 WASM 文件、许可证和启动自检。

### 7.4 结果与审核

每次求解保存：

- 输入快照和哈希；
- 课程班、候选时段、候选教师、教师资质和地点版本；
- 约束与目标权重版本；
- 求解器版本、状态、耗时和结果哈希；
- 已排班级、未排班级和安全的阻断原因；
- 选中候选方案及全部展开课次。

求解状态：

`draft → solving → solved/partially_solved/infeasible/failed → approved/archived`

求解结果只进入草稿。管理员确认后才成为正式课表；失败、超时或无解不能覆盖已有正式课表。

## 8. 后台任务、接口与状态

### 8.1 新增后台任务

- `student.basic.extract`：批量基础信息识别；
- `student.evidence.extract`：指定学生的文件事实提取；
- `course.recommend`：画像驱动课程推荐；
- `schedule.solve`：班级课表优化。

任务只携带批次或快照 ID、授权上下文引用和版本身份，不携带原始学生正文、电话或模型完整响应。

### 8.2 服务端接口

主要接口按领域提供：

- 批量建档：创建批次、读取结果、设置目标学生、逐条审核和应用；
- 学生增量：上传证据、读取建议、修改/接受/拒绝建议；
- 课程管理：课程模板、班级、教师、地点和候选时段的版本化维护；
- 课程推荐：创建推荐任务、读取推荐草稿、转换为人工课程规划；
- 排课：创建求解任务、读取冲突与结果、确认或废弃方案。

导入和建议状态：

`uploaded → queued → extracting → review_ready → partially_applied/applied/failed`

### 8.3 权限

- 批量建档、教师、地点和排课配置仅管理员可写；
- 顾问只能处理被授权学生的增量材料、建议、画像和推荐；
- 课程研发角色可维护课程模板草稿，但不能读取无关学生信息；
- 所有学生接口继续使用服务端生成的学生级授权上下文；
- Worker 执行前和写入前都必须重新验证账号、授权、批次、学生和快照身份；
- 浏览器不得持有 DeepSeek、PostgreSQL、对象存储或求解器管理凭据。

## 9. 测试与验收

### 9.1 自动化测试

- 使用合成 CSV 模拟真实文件的 BOM 表头、空白尾列、学生独立列、独立教师/日期、空反馈和格式异常；不得把真实教学反馈文件提交为测试夹具；
- 基础导入覆盖四种文件格式、重复候选、兄弟姐妹共用电话、无英文名、无效日期、模型无效 JSON、重试和批次幂等；
- 增量提取覆盖跨学生列隔离、DOCX 正文、逐条编辑/接受/拒绝、并发修订、证据定位、事实版本和画像 `needs_review` 传播；
- 自动扫描队列、日志、API 错误和审计记录，确保不包含家长电话、原始逐字稿或完整模型响应；
- 推荐测试确保模型不能引用候选集合外课程、未批准画像或其他学生 claim；硬规则违反漏检必须为 0；
- 排课测试覆盖教师资质、教师分配、教师冲突、地点冲突、不可用时间、周课递归、连续短期营、优先级、时段惩罚、教师空档、锁定课表、部分可行、无解和超时；
- 数据库迁移必须从空数据库和现有开发数据库分别验证；
- 所有任务覆盖幂等、有限重试、Worker 重启、租约接管和失败终态；
- 完整流程纳入真实 PostgreSQL、Redis/BullMQ 和 Web HTTP 端到端测试。

### 9.2 性能边界

- 单批最多 200 名学生或 20 MB；
- 单次增量文件不超过 20 MB；
- 单次排课最多 200 个班级；
- 每个班级最多 30 个候选方案；
- 单次求解时间上限 30 秒；
- 超出限制时在任务创建阶段拒绝，不允许拖垮 Worker。

### 9.3 业务试点

业务验收至少需要：

- 10 名受控学生；
- 3 份基础信息批次；
- 5 份教学反馈 CSV；
- 5 份会议 DOCX；
- 两组真实排课问题；
- 一份经批准的课程模板、班级、教师、地点和候选时段清单。

没有完成真实受控试点前，只能声明技术实现完成，不能声明业务阶段完成。

### 9.4 验收标准

- 未审核模型结果写入正式档案次数为 0；
- 跨学生信息进入模型输入或事实建议次数为 0；
- 接受的事实均具备合法来源定位；
- 新事实能够稳定触发画像和规划复查；
- 模型不能自动覆盖人工确认字段或已批准画像；
- 推荐课程硬规则违规数为 0；
- 每项推荐理由引用合法的已批准画像 claim；
- 正式课表中的教师均满足课程资质，且教师和地点重叠数为 0；
- 相同排课输入能够产生相同方案和结果哈希；
- 模型或求解器不可用时，手动事实、手动画像和人工课程规划仍可使用；
- PostgreSQL 和对象存储备份能够实际恢复，Meilisearch 可从正式数据重建。

## 10. 输入门禁与明确非目标

### 10.1 开发输入门禁

开始真实数据试点前，项目负责人需要确认：

- 学生基础信息字段、标准年级格式和电话规范化规则；
- 哪些身份和联系信息允许在最小化后发送至 DeepSeek；
- 顾问和管理员上传真实资料前的授权确认文本；
- 当前课程模板、课程规则和已完成课程名称映射；
- 教师名单、教师可用时间、地点和候选课表；
- 班级优先级和非首选时段惩罚规则；
- 真实试点学生、反馈 CSV 和会议 DOCX 的授权范围；
- 课程推荐和排课结果的业务验收负责人。

缺少上述输入时可以继续开发和使用脱敏合成夹具，但不得使用虚构结果代替业务确认。

### 10.2 本阶段明确不包含

- 学生自动分班；
- 班级文本名单与学生画像建立正式关联；
- 学生或家长独立账号与门户；
- 自动报名、缴费或候补管理；
- 自动向企业微信或其他外部平台发送消息；
- 根据模型建议自动修改或批准画像；
- 根据推荐自动加入班级名单；
- 由求解器选择地点；
- 未经管理员批准自动发布课表；
- 录取概率预测；
- Multi-Agent、Skill Registry 或复杂工作流平台化；
- 用匿名讲座案例填补当前学生未确认事实。

本阶段仍坚持：学生事实、证据、权限、课程硬规则和正式状态由确定性代码控制；DeepSeek只负责结构化识别与解释草稿，HiGHS只负责在确定约束内求解候选时段，最终结果均由人工审核和批准。
